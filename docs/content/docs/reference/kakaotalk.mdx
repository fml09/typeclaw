Part of the [channel adapters](/docs/reference/channel-adapters) family.

Transport: **LOCO protocol** (no public URL required). Setup walkthrough: [Add a channel](/docs/guides/add-a-channel).

<Callout type="warn" title="Use a dedicated account">
  Auto-acking every received message is a distinct non-human fingerprint. KakaoTalk abuse detection may ban accounts
  that exhibit this pattern. Run this adapter only on dedicated agent accounts you can afford to lose.
</Callout>

## Auth

Sub-device login using email and password. Passwords are stored **encrypted at rest** (AES-256-GCM; the key lives outside the agent folder).

Unlike the other adapters, `secrets.json#channels.kakaotalk` is not a flat credential object — it wraps one or more account records:

```json
{
  "channels": {
    "kakaotalk": {
      "currentAccount": "<accountId>",
      "accounts": {
        "<accountId>": {
          "account_id": "<accountId>",
          "oauth_token": "…",
          "user_id": "…",
          "device_uuid": "…",
          "device_type": "pc",
          "created_at": "…",
          "updated_at": "…"
        }
      }
    }
  }
}
```

| Field                  | Notes                                                   |
| ---------------------- | ------------------------------------------------------- |
| `currentAccount`       | `string \| null` — active account id, or `null` if none |
| `accounts.<accountId>` | Map of account id → account record (fields below)       |

Each record under `accounts.<accountId>`:

| Field               | Notes                                                          |
| ------------------- | -------------------------------------------------------------- |
| `account_id`        | Account identifier (matches the map key)                       |
| `oauth_token`       | Current session token                                          |
| `user_id`           | KakaoTalk user ID                                              |
| `device_uuid`       | Registered device UUID                                         |
| `device_type`       | `'pc'` or `'tablet'`                                           |
| `created_at`        | Record creation timestamp                                      |
| `updated_at`        | Last-update timestamp                                          |
| `refresh_token`     | _optional_ — refresh token when present                        |
| `auth_method`       | _optional_ — `'login'` or `'extract'`                          |
| `email`             | _optional_ — login email used by the renewal fallback          |
| `encryptedPassword` | _optional_ — AES-256-GCM envelope used by the renewal fallback |

A `pendingLogin` record may also appear under `channels.kakaotalk` mid-reauth; see [`secrets.json`](/docs/reference/secrets-json) for the full schema.

CLI: `typeclaw channel add kakaotalk` (interactive). **Do not use `channel set`** for credential rotation — use `typeclaw channel reauth kakaotalk` instead.

## Experimental Android main profile

The normal TypeClaw login uses the tablet sub-device profile. The fork also
exposes an experimental `android-main` profile that sends `dtype=1` and uses a
fresh device UUID when requested. Use it only with a disposable KakaoTalk
account: the mobile/main-device flow may invalidate or log out an existing
phone session.

From the host, request a fresh credential instead of reusing the saved tablet
UUID:

```sh
TYPECLAW_KAKAO_DEVICE_TYPE=android-main \
TYPECLAW_KAKAO_NEW_DEVICE=true \
typeclaw channel reauth kakaotalk
```

The command prompts for the account password. If Kakao returns `-100`, approve
the displayed passcode in the official KakaoTalk app and wait for registration
to complete. Do not use `--force` unless losing the test account's existing
session is acceptable. After login, verify
`secrets.json#channels.kakaotalk.accounts.<account>.device_type` is
`android-main`.

This profile is protocol-experimental. A successful `LOGINLIST` and `WRITE`
do not prove that `MODIFYMSG` is supported; verify the actual edited message
and its persisted history before enabling progress.

## Capabilities

| Feature                 | Supported | Notes                                                                                                                                                 |
| ----------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Outbound messages       | yes       |                                                                                                                                                       |
| Reactions               | limited   | HTTP endpoint; verified for `like`/`+1`/`👍`, `eyes`/`👀`, `heart`/`❤️`, `laugh`/`😂` — everything else is rejected as `unsupported`                  |
| Message editing         | limited   | LOCO `MODIFYMSG`; the current raw test account accepted text edits with status `0`, but a fresh `android-main` credential still requires verification |
| Typing indicator        | DM/group  | Animated "…" composing dots via the sub-device LOCO session; **not** OpenChat (see below)                                                             |
| Channel-name resolution | yes       |                                                                                                                                                       |
| Self identity           | yes       | Resolved from the authenticated `getProfile()` `user_id` and nickname                                                                                 |
| History                 | yes       | Limit 200 messages                                                                                                                                    |
| Attachments             | yes       | Files sent before text; no combined text+file send in one call                                                                                        |
| Membership              | no        |                                                                                                                                                       |

## Token renewal

Tokens expire after ~7 days. A host-side renewal cron first attempts a lightweight OAuth refresh grant using the stored refresh token, without decrypting or sending the password. If the refresh token is absent or KakaoTalk rejects it, renewal falls back to password-based login with the saved device UUID. Transient refresh failures do not trigger password login; the next daily tick retries. A successful renewal hot-reloads the KakaoTalk adapter through the host daemon, with a full container restart only as a transport fallback. If automatic renewal cannot proceed, re-authenticate with:

```sh
typeclaw channel reauth kakaotalk
```

## Quirks

- **KICKOUT recovery**: if the same `device_uuid` logs in elsewhere, the adapter detects the KICKOUT event and retries with bounded backoff (2s / 10s / 60s, 5-minute budget total).
- **Typing indicator**: emits the LOCO `ACTION` packet (`type=1`) from the sub-device session so the recipient sees the animated "…" composing dots. KakaoTalk auto-expires the indicator ~5s after the last packet, so the adapter registers a 4s router heartbeat (below the ~5s expiry, leaving margin for scheduler/network jitter, and faster than the default 8s) via `setTypingHeartbeatInterval` — the router paces the refresh and the callback stays stateless. There is no stop API; a delivered message clears the indicator client-side. Typing is classified **live at each tick**: authoritative DM/group rooms **and provisional rooms** send, only a room the resolver has no live entry for is treated as unresolved and skipped silently. **OpenChat (`@kakao-open`) is not supported**: the LOCO `ACTION` packet requires a `linkId` for open chats that the channel resolver does not surface today (the same limitation as mark-read), so a confirmed OpenChat is skipped and logged once per chat. A provisional room is always bucketed `@kakao-group` (never `@kakao-open`), so sending there is safe; in the rare case a provisional room is actually an OpenChat, the linkless `ACTION` fails soft — `sendTyping` throws on the non-success status and the callback swallows it as a per-tick warning. Wiring `linkId` through the resolver (to support typing inside open chats) is a shared follow-up.
- **Mark-read**: fires on every inbound message, clearing the unread "1" (노란숫자), except in open chats.
- **Provisional registration**: chats not surfaced by `getChats` are registered provisionally on first message.
- **No combined send**: files are sent first, then text, as separate API calls.
- **Split messages**: users often send one thought as several rapid bubbles, and the default router debounce (600ms/1500ms) can start a turn on the first bubble alone. Set `inboundBatching` (`quietMs: 2500`, `maxWaitMs: 6000` is a good start) to wait for a quiet gap and answer all bubbles in one turn.
- **Steer (mid-turn injection)**: by default a bubble that arrives while the agent is still answering waits for the next turn. `steer: { "enabled": true }` injects it into the RUNNING turn instead (after a `quietMs` coalescing window), so a follow-up like "그리고 테스트도 돌려줘" lands while the work is still in progress. Attachments and reply-quotes always take the normal queued path. See [/reference/channel-adapters](/docs/reference/channel-adapters).
- **Reactions**: `channel_react` posts an emoticon-pack reaction through KakaoTalk's HTTP reaction endpoint (independent of the LOCO device profile). Four reactions are live-verified — like (`1200282_026`), eyes (`1200509_012`), heart (`1200281_001`), laugh (`1200282_002`) — and other emoji names map to `unsupported` rather than guessing an ID. The endpoint rejects integer reaction values with HTTP 400, so only these catalog string IDs are sent.
- **Message editing**: `channel_edit` maps to LOCO `MODIFYMSG` and can edit only a message authored by the agent. A raw test-account probe accepted the exact text packet with status `0`; the CLI/SDK must omit `extra` for default text edits because Kakao returned `-303` when `{}` was sent. Verify the replacement in the KakaoTalk client before enabling progress.

## Config

```json
{
  "channels": {
    "kakaotalk": {
      "enabled": true,
      "engagement": {
        "trigger": ["mention", "reply", "dm"],
        "stickiness": { "perReply": { "window": 900000 } }
      },
      "history": {
        "prefetch": {
          "thread": { "head": 3, "tail": 10 },
          "channel": { "tail": 10 }
        }
      },
      "quotedReply": { "enabled": true, "queueDelayMs": 10000 },
      "inboundBatching": { "quietMs": 2500, "maxWaitMs": 6000 },
      "postReplyReaction": { "enabled": true, "emoji": "like" },
      "progress": {
        "enabled": true,
        "updateIntervalMs": 1000,
        "toolLog": true,
        "startReaction": "like",
        "successReaction": "like",
        "errorReaction": "like"
      },
      "reactionTrace": { "enabled": true, "maxEvents": 100, "includeUnknownMethods": true },
      "steer": { "enabled": true, "quietMs": 2500 }
    }
  }
}
```

`reactionTrace` is a temporary, opt-in diagnostic setting for KakaoTalk. It
logs bounded inbound LOCO packets for reaction protocol discovery while
redacting message contents and credentials. Set `includeUnknownMethods` to
`true` when the reaction push method is not known yet. Disable it after
collecting a protocol fixture. Credentials live in
[`secrets.json#channels.kakaotalk`](/docs/reference/secrets-json).
